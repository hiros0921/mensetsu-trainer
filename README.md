# MENSETSU — 面接シミュレーター

AI 面接を模した練習アプリ。エンジニア面接・圧迫面接・英語面接の3モードを、
サーバー側のステートマシンで進行させ、終了後に5軸の内訳つきで判定を出す。

Java 21 / Spring Boot 3.5 / PostgreSQL 17 / Claude API。

**この README は機能一覧ではなく、設計判断とその根拠を書いたものです。**
何ができるかは動かせば分かるので、なぜそう作ったかを残します。

---

## 動かし方

必要なもの: **JDK 21** と **Docker**。それ以外の準備は要りません（Gradle は同梱の `./gradlew`）。

### APIキー無しで動かす（2コマンド）

```bash
docker compose up -d      # PostgreSQL 17。ポート 55433（他と衝突しないようずらしてある）
./gradlew :app:bootRun    # http://localhost:8080 を開く
```

**キーが無くても、面接を最後まで通せて判定まで出ます。** 質問は組み込みのスタブが作ります。
画面上部に「スタブで動いています。APIキーが未設定です」と出るので、どちらで動いているかは常に分かります。

テーブルは起動時に Flyway が作ります（V1〜V5）。DB の作成手順はありません。

### 本物の Claude API で動かす

```bash
cp .env.example .env && chmod 600 .env    # ANTHROPIC_API_KEY= に自分のキーを書く
./gradlew :app:bootRun
```

`.env` は `.gitignore` 済みで、リポジトリには入りません。キーを `application.yml` にも書いていません。

### 止める / 作り直す

```bash
docker compose down       # 止める（データは残る）
docker compose down -v    # データごと消す。次の起動でマイグレーションが最初から走る
```

### 中身を確かめる

```bash
./gradlew build                    # テスト164件（DB も API も要らない）
./gradlew :domain:walkthrough      # 面接を1回、LLM なしで通す
./gradlew :domain:policycompare    # 基準の案を同じ面接に当てて比べる
./gradlew :domain:pressurepolicy   # 圧迫面接の案 × 圧の設定
./gradlew :domain:englishpolicy    # 英語面接の案 × 入力方式
./gradlew :app:webrun --args="ENGINEER"   # 起動中のアプリに繋いで通す（課金あり）
```

## 設計判断

### 1. なぜステートマシンをドメイン層に置き、Spring から独立させたか

`domain` と `app` は Gradle のモジュールとして分けてあり、**`domain` は Spring に依存できません**。
依存の向きは `app → domain` の一方向だけです。

面接の進行（フェーズ遷移・掘る段数・圧の計算・打ち切り）は、このアプリの中身そのものです。
ここが Spring の管理下にあると、遷移を1つ確かめるのに DI コンテナの起動が要る。
起動に数秒かかるテストは、細かい条件を並べて書く気がなくなります。書かなくなった条件は、
そのまま確かめていない条件になります。

いまは `new InterviewMachine(new StubEngine())` だけでテストが書けます。
164件のテストは DB も API キーも要りません。

この分離は口約束では守れないので、テストで縛ってあります
([DomainIsolationTest](domain/src/test/java/jp/lightech/mensetsu/domain/DomainIsolationTest.java))。
`domain` のクラスパスに Spring が現れたら、そこで落ちます。

**外から遷移を指示できない形にしてあります。**
`InterviewMachine.submit()` が受け取るのは回答だけで、次のフェーズを渡す経路がありません。
画面から `{"type":"answer"}` は送れても、`{"phase":"RESULT"}` は送れない。
「フェーズはサーバー側で管理する」を、コメントではなくシグネチャで表しています。

### 2. なぜ LLM 呼び出しを抽象化し、スタブを用意したか

`InterviewerEngine` は `domain` 側のインターフェースで、その実装（`ClaudeEngine`）が `app` 側にあります。
依存性逆転です。ドメインは「観察してくれる誰か」を知っていますが、それが HTTP の向こうにいることは知りません。

理由は3つあります。

- **確かめたいものが違う。** 「圧が75を超えたら PRESSURE へ移る」を確かめるのに、LLM は要りません。
  スタブなら、掘りが尽きた／答えが曖昧だった／黙った、を狙って作れます。
- **LLM の出力は毎回違う。** 同じ台本でも返る観察が変わります。それを許したまま遷移のテストを書くと、
  落ちたときに「実装が悪いのか、今日の LLM がそう答えただけか」が分かりません。
- **API キーが無くても最後まで動く。** 採用面接で見せる相手に、キーを配らずに触ってもらえます。

`ClaudeEngine` は**例外を投げません**。落ちたら定型の相槌に落として面接を続けます。
練習アプリなので、途中で止まるほうが害が大きいためです。ただし失敗は `engine_calls` に残し、
画面にも「生成に失敗（相槌でつなぎました）」と出します。隠して続けることはしません。

### 3. なぜ時間の判定をサーバー側に置いたか

英語面接には制限時間（90秒）と沈黙の打ち切り（8秒）があります。
**クライアントが送るのは「入力があった」という事実だけです。**

```javascript
ws.send(JSON.stringify({ type: 'input' }));   // これだけ
```

何秒の沈黙とみなすか、打ち切るかどうか、回答に何秒かかったことにするかは、すべてサーバーが決めます。

クライアントに判定させると、こう壊れます。ブラウザのタブが裏に回るとタイマーが止まる。
端末の時計がずれていれば境目もずれる。画面側を書き換えれば制限時間を無効にできる。
練習アプリなので不正の心配は小さいのですが、**「どの端末で受けても同じ面接になる」**が崩れます。

時計（[AnswerClock](domain/src/main/java/jp/lightech/mensetsu/domain/interview/AnswerClock.java)）は
`System.currentTimeMillis()` を呼ばず、**現在時刻を引数で受け取ります**。
90秒の制限時間を試すのに90秒待たずに済みます。この作りにしていなければ、
猶予・沈黙・制限時間の境目のテストは書かれなかったはずです。

制限時間の値は `interviewer_profiles` テーブルにあります。コードには既定値しかありません。
「厳しい英語面接官」を足すのに、`UPDATE` 1行で済みます。

**ここで1つ失敗しています。** 制限時間を英語面接官にだけ持たせたところ、日本語の2モードで
時間そのものが記録されなくなり、沈黙の軸が「測れなかった」になりました。測れなかった軸は0点として
数えるので、圧迫面接は沈黙の25点を必ず落とし、満点が75点になっていました。合計点だけ見ていても
気づけません。**打ち切らないことと、測らないことは別**だったので、時計は全モードで動かし、
打ち切りだけを英語面接に限る形に直しました。同じ型の見落としを止めるため、
`Mode.values()` を回すテスト
([SilenceIsMeasuredEverywhereTest](domain/src/test/java/jp/lightech/mensetsu/domain/interview/SilenceIsMeasuredEverywhereTest.java))
を置いています。モードを足せば、そのモードも自動で見ます。

### 4. なぜ揺らぐ軸に大きな重みを置かなかったか

判定は5軸（具体性・簡潔さ・一貫性・深さ・沈黙）の加重和です。
このうち**一貫性は LLM に判定させています**。「前の発言と食い違っているか」は、文字列処理では測れません。

**同じ台本を2回流したら、結果が割れました。**

| 同じ入力 | 食い違いの検出 | 一貫性の素点 |
|---|---|---|
| 1回目 | 2回 | **71点** |
| 2回目 | 0回 | **100点** |

差は29点。これが合計点にいくら効くかは、その軸の重みで決まります。

| 案 | 一貫性の重み | 同じ人が2回受けたときの合計点の差 |
|---|---|---|
| 案R1（一貫性が主軸） | 40 | **11.6点** |
| 案R2 | 30 | 8.7点 |
| **案R3（採用）** | **25** | **7.3点** |
| エンジニア面接（採用済み） | 15 | 4.4点（参考） |

判定の境目は 88 / 74 / 58 / 42 です。**案R1 だと、同じ人が同じ答えをして判定が1段変わります。**
「実力ではなく運で判定が動く」状態です。

ここで採った立場は、依頼主（諏訪）の言葉がそのまま設計になっています。

> 「その軸が重要か」と「その軸に重みを置けるか」は、別の問題。
> 重要だからこそ、測れるようになるまで重みは下げる。ただし内訳表示では目立たせる。

そこで **重みと強調を別の概念として型で分けました**
（[ScoringPolicy](domain/src/main/java/jp/lightech/mensetsu/domain/scoring/ScoringPolicy.java) の
`weights` と `emphasised`）。一貫性は重みを25に留めたまま、内訳表示では色を付け、
「この判定は揺らぎます」の注記を必ず添えます。**点数に反映しないことと、本人に伝えないことは別です。**

同じ考え方を、英語面接では「入力方式で動く軸」に当てました。沈黙は音声入力でしか発生しません。
テキストで落ち着いて書けば、その軸は自動的に満点になります。実測すると、**同じ内容の受験者でも
入力方式を変えるだけで合計点がこれだけ動きました。**

| 案 | 沈黙の重み | 音声 → テキストで動く点数 |
|---|---|---|
| 案E-1（沈黙が主軸） | 35 | **+35点**（C47 → A82。2段） |
| **案E-2（採用）** | 25 | **+25点** |
| 案E-3 | 30 | +30点 |

案E-1 は「時間内に言い切れるか」を測るという意味では筋が通っていますが、
実質65点満点の勝負になり、判定が壊れます。

それでも案E-2 で25点は残ります。ここは作り込まず、**明示で対処**しました。
結果画面に受験した入力方式を出し、沈黙の内訳に
「すべてテキスト入力です。落ち着いて書けるぶん、音声で受けた場合よりこの点は高く出ます」
と添え、開始画面で音声入力を推奨します。

> 測っていない条件を隠さない。

これは STAR 構造の扱いと同じです。「観察していない」と「無かった」を
[Star](domain/src/main/java/jp/lightech/mensetsu/domain/port/Star.java) 型の
`observed` フラグで分けてあります。英語面接以外では STAR を聞かないので、
そこで0点にすると全モードが減点されます。**測れなかったことは、0点ではありません。**

## 数値はすべて実測で決めた

重み・境目・圧の上がり幅・制限時間は、どれも案を並べて実際に採点し、分布を見てから選んでいます。
選定に使った道具はテストコードとして残してあり、いつでも再実行できます。

| 道具 | 決めたもの |
|---|---|
| `:domain:policycompare` | エンジニア面接の重みと境目（案A/B/C） |
| `:domain:pressuresweep` | 圧の上がり幅・下がり幅（案P1/P2/P3） |
| `:domain:pressurepolicy` | 圧迫面接の重み（案R1/R2/R3）× 圧の設定 |
| `:domain:englishpolicy` | 英語面接の重み（案E-1/E-2/E-3）× 入力方式 |

実行できる形で残しているのは、**基準を変えたくなったときに、同じ材料で選び直せるようにする**ためです。
実際、判定の妥当性を疑ったときに選定当時のコミットへ戻して同じ道具を回し、
分布が1点も動いていないことを確かめています。

測定（`Scorer` → `ScoreBreakdown`）と値踏み（`ScoringPolicy` → `Score`）も分けてあります。
面接をやり直さずに、過去の記録を別の基準で再評価できます。

## 作っていないもの

意図的に作っていません。プロトタイプとして必要な範囲を超えるためです。

- 音声合成（読み上げ）。音声は**入力のみ**で、ブラウザ内で文字列にしてから送ります。
  **音声データはサーバーへ送信も保存もしません。**
- 3Dモデル・アニメーション。面接官の表情は5枚の静止画と CSS のフェードだけです。
- 認証基盤・決済・複数テナント・本番デプロイ。
- 中断した面接の復帰。ただし**セッション状態は DB に持ち続け**、後から足せる形にしてあります。
  中断は `ABANDONED` として記録し、履歴とスコア集計から除外します（混ぜると平均点が意味を失うため）。
  除外はビュー（`completed_sessions`）側に持たせてあり、画面ごとに条件を書き忘れられません。
  ただし「中断が何件あったか」は画面に出します。混ぜないことと、無かったことにするのは別です。

## 構成

```
domain/   面接の進行と採点。Spring も DB も LLM も知らない
  interview/   ステートマシン・圧・掘り・時計・表情
  scoring/     測定（Scorer）と値踏み（ScoringPolicy）
  port/        LLM に何を観察させるかの取り決め
  stub/        LLM なしで動かすための面接官
app/      HTTP・WebSocket・DB・Claude API
  web/         WebSocket 進行、履歴 API、放置セッションの片付け
  llm/         Claude API アダプタ（ストリーミング・構造化出力）
  store/       SQL 直書き（JSONB・部分インデックス・CHECK 制約を使うため）
  resources/db/migration/   Flyway V1〜V5
```

テスト164件。`./gradlew build` で全部通ります。DB も API キーも要りません。
